# Quantity pricing transition

Buyer-facing quantity prices are on: shared catalogue reads project the **approved** quantity price revision, so a published product shows the table the supplier uploaded. `VEXIM_QUANTITY_BUYER_PREVIEW=false` is now only an escape hatch that turns that projection off; it is **not** an access-control mechanism. `VEXIM_QUANTITY_PRICING_PREVIEW` is unchanged (extra internal supplier editor, staging only).

Supplier product creation and editing use the quantity-price editor rather than the legacy grade table. Creating a supplier product atomically saves a validated private pending price; suppliers no longer enter an English name. When an eligible never-published product is submitted for review, the existing AI translator runs if configured. Its write is conditional on the submitted product version and review state, and the CRM reviewer can edit the translation. Translation failure does not prevent submission; the supplier is told staff must complete it. `OPENAI_API_KEY` must be configured for AI. Migrations `20261057` through `20261060` must be applied in order after `20261053`–`20261056`. Without the new RPCs, new creation or submission fails closed. Retries use an idempotency key; pending proposals never replace the previously approved price. A changed product must have a matching price before submission.

Publishing a new-flow product does **not** need a separate price approval: the reviewer who approves the product is looking at its table, so the database approves the **first** price in the same transaction (`20261078`, which also records `reviewed_by`/`reviewed_at` on that revision). Only later **updates** keep their own review step — once an approved price exists, publishing never approves a newer pending revision, and the buyer keeps seeing the approved table until staff approve the new one. Publication no longer depends on a deployment flag; the old `p_buyer_enabled` argument is deprecated and ignored.

Existing public legacy price fields are deliberately preserved when suppliers or CRM staff edit other product details. The CRM edit form uses the quantity editor; CRM product creation and CSV import still contain legacy pricing paths, and the storefront and other buyer paths still depend on legacy data. These are not dead code and must not be deleted or treated as fully migrated yet. Staff price proposals require an attestation of the supplier's commitment; the audit log is best-effort, not a durable consent ledger.

- `VEXIM_QUANTITY_PRICING_PREVIEW=true` exposes an additional internal supplier editor for approved suppliers and their own eligible products. Submissions write real pending revisions and use the CRM review queue. Use a dedicated staging database and test accounts.
- `VEXIM_QUANTITY_BUYER_PREVIEW=false` disables the buyer projection described above (home, search, category cards, product detail and comparison). Leave it unset in normal deployments.

Only approved revisions are projected; pending revisions never replace them. The existing supplier public-price consent gate still applies. Approved prices remain visible past the configured staleness threshold, but are excluded from category reference ranges and price ranking. If no new approved price exists, the legacy projection is retained. Settings or revision read failures fail closed (the catalogue does not invent a price), but a single approved revision that cannot be read as a price is skipped with a server log so one bad row cannot take the catalogue down.

The supplier storefront has a separate legacy projection. AI translation into a separately reviewed editable name for already-published products, product-family cloning, reminders, reconfirmation, promotions and a durable consent history remain incomplete. Existing approved or pending English-name revisions and staff-edited names are preserved and not automatically replaced; the buyer preview still prioritizes an approved name revision over the product translation. Some older English names can still contain legacy grades. Staff must check the English name before publication, particularly if AI was unavailable. Naming, CRM/import workflows and the remaining buyer paths still mix legacy data: check the English name before publishing, and do not migrate legacy multi-grade records automatically.
